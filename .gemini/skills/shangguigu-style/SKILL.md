# 尚硅谷风格技术讲义与教程写作指南 (Shangguigu Style Guide)

尚硅谷（Shangguigu）的讲义风格在大数据（Hadoop、Spark、Flink、ClickHouse）和后端领域被广大工程师公认为“新手入门天花板”。其核心魅力在于：**彻底破除技术黑话与繁冗业务包装，用最直观的方式讲透技术本质，给读者提供 100% 确定性的实操反馈。**

无论编写什么技术（数据库、数据仓库、云原生、中间件），凡需产出新手友好、深入浅出的教程或博客，均必须遵循本规范。

### 原则一：开门见山，极简对比（Simplicity First & Visual Contrast）

> **“不搞高深的概念包装，用小学生都能看懂的图表，一秒讲透技术本质。”**

- **反面典型（反模式）**：
  一上来引用维基百科或学术论文定义：“OLAP 是面向分析的以多维模型组织的数据处理系统，具备复杂聚集与多维下钻能力……”，读者读完三遍依然云里雾里。
- **尚硅谷标准做法**：
  在讲“行存储 vs 列存储”时，绝不堆砌理论，直接画一个只有 3 行 3 列的极简表格：
  ```
  【逻辑表】
  Id   Name   Age
  1    张三   18
  2    李四   22
  3    王五   34

  【行式存储在磁盘上的字节排列】：
  1 张三 18  2 李四 22  3 王五 34
  -> 好处：查张三的所有属性，一次磁盘顺序寻址搞定。
  -> 弊端：想查所有人的平均年龄，必须扫完全表跳过不需要的名字。

  【列式存储在磁盘上的字节排列】：
  1 2 3  张三 李四 王五  18 22 34
  -> 好处：查所有人的年龄直接把最后一列抽出来，连续读取，压缩率极高！
  ```
- **落地要求**：
  - 核心架构或机制（如存算分离、分区与索引、主从复制），必须提供**极简对比图解**；
  - 善用现实世界通俗隐喻或直观排布，彻底拉平读者的背景认知差。

---

### 原则二：去业务化，聚焦底层技术（De-businessify & Pure Tech Focus）

> **“技术讲义一旦掺杂复杂业务，读者 80% 的精力会被浪费在理解业务上，反而丢了技术本身。”**

- **反面典型（反模式）**：
  用“银行核心结算”、“证券对冲交易”、“医药审批流程”作为案例，测试建表写了 50 个业务字段，包含利息复利算法，读者被业务逻辑搞得晕头转向。
- **尚硅谷标准做法**：
  测试数据永远保持极简通用的工程字段，只服务于技术特性的验证：
  ```sql
  -- 极简技术验证表
  CREATE TABLE test_a (
      user_id     UInt64,
      score       String,
      deleted     UInt8 DEFAULT 0,
      create_time DateTime
  );
  ```
- **落地要求**：
  - 测试表字段控制在 3~6 个，命名直观（`id`, `name`, `status`, `updated_at`, `content`）；
  - 关注技术特性（数据类型、压缩比、去重合并、CDC 状态），避免任何特定行业的业务暗语。

---

### 原则三：三板斧闭环实操（Three-Piece Action Loop）

> **“每个小节都形成严密的自闭环：痛点引出 -> 语法/参数字典 -> 完整命令与真实回显。”**

每一个功能点、每一道工序，均按以下三步曲展开：

```markdown
#### 1. 痛点引出（为什么需要它？）
说明原生操作或默认机制的局限（例如：ReplacingMergeTree 默认只在后台合并，查总数还是 10500000 条，并没去重）。

#### 2. 基本语法与核心参数字典
给出标准化语法模版，并提供表格化的参数解释（字段名、默认值、生产建议值）。

#### 3. 案例实操与控制台真实回显（所见即所得）
给出立即可运行的完整代码，紧随其后附上终端/控制台打印出来的真实输出：
> **控制台执行结果**：
> ```text
> Query id: 3a92f8e1-92b1-4c12
> ┌─user_id─┬─score─┬─ctime───────────────┐
> │       1 │ AA    │ 2026-10-28 22:00:00 │
> └─────────┴───────┴─────────────────────┘
> 1 row in set. Elapsed: 0.005 sec.
> ```
```

- **落地要求**：
  - **绝不贴假代码**：所有命令必须经过真机验证；
  - **带出真实指标**：标明执行耗时（如 `145ms`）、返回行数（如 `20 rows`）或执行截图，杜绝读者盲猜。

---

### 原则四：直面暗坑，实战避险（Direct Pitfalls & Battle-tested Solutions）

> **“不报喜不报忧，把官方手册里藏着掖着或者最容易踩坑的暗礁直接挑明。”**

- **反面典型（反模式）**：
  照搬官方 Happy Path 文档，读者一到真实环境运行立刻因权限、路径、编码或版本报错，甚至误以为系统丢数据。
- **尚硅谷标准做法**：
  在章节标题或显眼位置直接打上 **`【重点】`**、**`【避坑指南】`**：
  - 例如：“*ReplacingMergeTree 只是保证最终一致性，在未合并前会出现短暂数据不一致的情况！*”
  - 随后给出工业界 3 套标准避险解法（手动 OPTIMIZE、Group By argMax 去重、FINAL 修饰符），分析各自的性能与适用场景。
- **落地要求**：
  - 记录真实报错信息（如 `unexpected 'コン'`、`AI function is not available for trial accounts`）；
  - 给出报错根因分析，并提供 100% 修复代码。

---

### 原则五：环境前置，零隐式假设（Transparent Prerequisites）

> **“绝不在正文开始后突然让读者去补环境依赖。”**

- **反面典型（反模式）**：
  让读者执行到第 5 步，突然报错“找不到某目录”、“缺少某依赖”或“端口被占用”。
- **尚硅谷标准做法**：
  每一模块或全书开篇，必设 **【准备工作 / 前置检查】** 小节：
  - 操作系统与版本号；
  - 防火墙状态、最大文件句柄限制（`nofile 65536`）；
  - 依赖软件包与服务连通性检查命令。
- **落地要求**：
  - 读者从空白环境开始，按顺序复制执行每一条命令即可顺利跑通，全程无需额外“搜百度求助”。

## 三、写作评审自检清单 (Writer Checklist)

在定稿前，请作者或评审 Agent 对照本清单逐项勾选：

- [ ] **是否消除了行业业务干扰？**（没有银行、保险、电商等特定业务规则，只有纯技术字段）。
- [ ] **是否有极简对比图？**（是否有类似“张三李四”的直观排布图让新手秒懂）。
- [ ] **参数字典是否齐全？**（涉及的配置项是否有表格逐项列出建议值与说明）。
- [ ] **实操是否带真实回显？**（执行结果是否展示了真实耗时、行数或真实截图）。
- [ ] **是否收录了典型报错与避坑方案？**（读者踩坑后能否直接在文内找到解法）。
